## 结论与范围

基线 `c7ba4c0`。本次只诊断 `TestOnlineDLPCountsDroppedWhenQueueFull`，不修改生产代码或现有测试。先复现原失败，再比较调度、明确的 worker 握手、作业计数、资源条件与 race；不能仅凭“重跑有时通过”认定是时序。

本次证据支持：**原断言缺少“第一条作业已由 worker 取走”的先行关系，不能保证三次提交恰好接受两条。** 在该生产实现的非阻塞语义下，第一条仍占队列时，第二、第三条都允许被计数丢弃。全部受控探针中，已接受的合成作业均被唯一分析、落库；没有观察到它们额外消失、计数竞争或资源耗尽。这个结论限于下述输入与调用生命周期，不能推广为整个采集端不存在并发问题。

## 因果对照与计数

通过 Go `-overlay` 给原测试文件追加诊断用例，生产文件不替换、不修改。三个模式只改变首 worker 的执行条件：

1. 未握手：仍连续 submit 三项；关闭 gate 后 close 排空，记录实际 dropped/frames/hits/存储ID。
2. worker握手：提交第一项，等待假存储通过 channel 明确报告“已进入 AppendFinding”；此时首 worker 必然已取走并识别第一项，才提交第二、第三项。没有新增 sleep。
3. 延迟worker：用同一生产 submit/worker 方法构造受控交错，三项都提交后才启动 worker。这是“worker尚未获调度”的模型对照，不冒充原构造函数路径。

各模式在每种CPU配置下1000轮；分别运行普通、16MiB软限制、race版本。

| 模式 | 实际接受 | dropped | 排空后 frames/hits/存储数 | 观测 |
|---|---:|---:|---:|---|
| 未握手，普通版本 | 1 | 2 | 1 / 1 / 1 | 三种CPU各1000轮均如此 |
| 明确worker握手 | 2 | 1 | 2 / 2 / 2 | 三种执行条件、三种CPU各1000轮，全部符合 |
| 延迟worker | 1 | 2 | 1 / 1 / 1 | 三种执行条件、三种CPU各1000轮，全部符合 |

race未握手版本CPU2有4/1000轮、CPU8有3/1000轮接受两项，其余接受一项；均满足提交总数守恒。诊断版本抑制重复日志，输出时机与原测试不同，因此不以两者失败率相等作为证据。

同时逐条检查接受作业的ID没有重复，并断言（仅针对此全部命中、存储成功的输入）：`submitted = frames + dropped`、`frames = hits = unique stored`。每组3000轮结束，goroutine数均为2→2。另以附录中的最小握手用例，在正常日志输出、race下 `-cpu=1,2,8 -count=1000` 再验证3000轮，退出码0。

## 容量、资源与故障分类

先握手占住每个 worker，再连续提交至总数100000；gate放行前队列长度等于配置容量，放行后所有接受项唯一落库。下表在三种CPU、普通/16MiB/race条件下结果相同：

| Workers / QueueSize | gate前分析中 / 排队 | dropped | 排空后 frames / hits / unique stored |
|---|---:|---:|---:|
| 1 / 1 | 1 / 1 | 99998 | 2 / 2 / 2 |
| 2 / 1 | 2 / 1 | 99997 | 3 / 3 / 3 |
| 4 / 8 | 4 / 8 | 99988 | 12 / 12 / 12 |

没有观察到已接受项无计数丢失。`runtime.MemStats.Alloc`采样约1.1–4.2MB，会受GC影响；它不是RSS、峰值或容量证明。16MiB是Go软限制，不是操作系统硬内存限制；系统物理内存查询受沙箱限制，本次不据此声称真实环境不存在内存压力。

故障注入让假存储对所有 AppendFinding 返回错误：提交3项、明确握手后得到 `frames=2,dropped=1,hits=0,stored=0`。这说明“hits少于提交数”还可能来自落库失败；本次原假存储从不返回错误，且已经验证接受项守恒，不能用这种故障解释原失败。生产 dropped 目前仅计队列满，落库错误另写日志，二者不可混算。

既有5项DLP回归（脱敏落库、阈值过滤、载荷截断、禁用配置、非法级别）在race下×10次×3种CPU，**150/150通过，无race报告**。未做真实网卡、长期吞吐、故障磁盘、并发close/submit或HTTP快照生命周期验证；“无race报告”只适用于已执行路径。

## 建议

根代理独立审阅后，可把原用例改为显式等待“worker已进入假存储”，再填队列和触发回压；保留超时保护和退出清理，额外断言 dropped精确值、队列容量及最终存储数。不要通过固定sleep、增加队列容量、降低期望hits或强制GOMAXPROCS掩盖问题。

当前证据没有要求改变生产 submit 的非阻塞语义或增加生产启动等待。真实采集容量是否足够，应另用实际包速和队列丢弃指标验收；真实回压丢弃是现有契约允许的行为，不能因测试修正而宣称零丢包。

最小握手对照代码如下，可直接追加到原测试文件的**临时副本**；使用既有 `blockingStore` 和原文件imports，无需修改任何生产代码。下面仅此一个Go代码块，供后续脚本自动提取。

```go
type p0ReadyStore struct {
    *blockingStore
    entered chan struct{}
}

func (b *p0ReadyStore) AppendFinding(f storage.DLPFinding) error {
    b.entered <- struct{}{}
    return b.blockingStore.AppendFinding(f)
}

func TestP0ReadyHandshake(t *testing.T) {
    fake := &p0ReadyStore{
        blockingStore: &blockingStore{gate: make(chan struct{})},
        entered: make(chan struct{}, 2),
    }
    cfg := config.DLPConfig{Enabled: true, QueueSize: 1, Workers: 1, MaxPayload: 1024, MinLevel: "SAFE"}
    p, err := newDLPPipeline(fake, cfg)
    if err != nil { t.Fatal(err) }
    released := false
    defer func() { if !released { close(fake.gate) }; p.close() }()
    job := dlpJob{payload: []byte("联系电话 13800138000"), payloadBytes: 16, proto: "tcp"}
    p.submit(job)
    select {
    case <-fake.entered:
    case <-time.After(2 * time.Second): t.Fatal("worker did not enter AppendFinding")
    }
    p.submit(job)
    p.submit(job)
    if len(p.jobs) != 1 || p.frames.Load() != 1 || p.dropped.Load() != 1 {
        t.Fatalf("blocked: queue=%d frames=%d drops=%d", len(p.jobs), p.frames.Load(), p.dropped.Load())
    }
    close(fake.gate)
    released = true
    p.close()
    if p.hits.Load() != 2 || p.frames.Load() != 2 || p.dropped.Load() != 1 || len(fake.appended) != 2 {
        t.Fatalf("drained: hits=%d frames=%d drops=%d stored=%d", p.hits.Load(), p.frames.Load(), p.dropped.Load(), len(fake.appended))
    }
}
```
