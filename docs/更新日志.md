## FlowMask v2 增补（未发版）—— 解码复核扩展到 URL-safe / hex / 两层嵌套 · 2026-10-21

> 承接同日「编码载荷解码复核」：补上常见的编码变体与二次编码，避免换个字母表/换个进制就绕过。

### 新增

- `server/app/identify/decode.py` 重写解码链：base64（标准 + URL-safe，可缺省 padding）、
  十六进制（连写 / `\xNN` 转义）、百分号编码，**最多两层嵌套**（`base64>percent`、`base64>base64`），
  命中规则里记录编码链（如 `decoded-base64>percent:mobile`）；
- 候选片段按「hex 转义 > 纯 hex > 百分号 > base64」优先级扫描，每个正则只接受首层解码类型相符的片段
  （修掉「短 hex 被 base64 候选误吃成 hex」的判定错位）；
- `Hit.direct_hint` + `scoring.score` 调整：编码层数只削弱证据强度（每层 ×0.95），
  但**不降低严重度**——身份证/银行卡/密钥的二次编码仍走「一票高危」直达 L3（`direct=true`）；
- `server/tests/test_decode.py` 扩到 **16 例**（URL-safe / hex / hex 转义 / 两层 base64 / base64 套百分号 /
  短 hex 负例 / 二进制负例 / 开关）。

### 验证

- `cd server && python -m pytest -o addopts="" -q` → **287 passed, 1 skipped**（288 用例）；
- 351 条主评测集（L2 = ONNX int8 真模型）仍为 **100.0%**、类别 Micro-F1 **0.888**、
  安全误报 **0.0%**——扩展解码没有引入新的误报；
- 示例：`base64(base64("身份证 11010519491231002X"))` → L3 直达；`hex("{\"phone\":\"13800138000\"}")` → L2。

## FlowMask v2 增补（未发版）—— 编码载荷解码复核（base64 / 百分号）· 2026-10-21

> 背景：评测集里唯一一条分级错误是 base64 编码的联系方式——`{"phone":"13800138000"}` 编码后
> 正则看不见手机号，但数据本体已经出去了。这一类「编码绕过」在真实泄露里很常见。

### 新增

- `server/app/identify/decode.py`：识别 base64（≥12 字符）与 URL 百分号编码（≥2 个 `%XX`）片段，
  解码后要求「像文本」（可打印 ≥90%）才复核，命中按 0.95 置信度折价后参与评分；
- `server/app/identify/scoring.py::analyze`：新增 `enable_decode` 开关（默认跟随
  `FLOWMASK_DISABLE_DECODE`），解码命中与明文命中去重合并后统一评分；
- 脱敏仍替换整段编码（不在正文里凭空插入字符），命中区间与原文自洽；
- `server/tests/test_decode.py`：10 例（base64 手机号 L2 / 身份证 L3 直达 / 整段替换 / 百分号编码 /
  纯文本不误报 / 二进制跳过 / 单次与全局开关 / 多片段顺序）。

### 验证

- `cd server && python -m pytest -o addopts="" -q` → **281 passed, 1 skipped**（282 用例）；
- 351 条主评测集（L2 = ONNX int8 真模型）：`L1 only` 准确率 **94.0% → 94.3%**、
  `L1+L2` **99.7% → 100.0%**（分级 Macro-F1 1.000、类别 Micro-F1 0.888、高危漏检 0.0%、安全误报 0.0%）；
- `python -m app.evaluate --compare-l2 --l2-endpoint http://127.0.0.1:8091/v1/classify` 可复跑。

## FlowMask v2 增补（未发版）—— L1 自由文本召回：叙述里的人名/地址也能抓 · 2026-10-21

### 新增

- `server/app/identify/rules.py` 补 4 条**自由文本**规则（内置规则 13 → 17 条）：
  - `name_free_role`：角色词（同事/客户/联系人…）+ 2~4 字姓名；
  - `name_free_sentence`：句首姓名 + 动作/时间词（反馈/提交/刚/已/在…）；
  - `name_free_action`：「由/请/向/给」+ 姓名 + 动作（整理/补充/提交…）；
  - `address_free`：省/市 + 区/县 + 路/街/大道 + 门牌号（支持「中关村大街 1 号」带空格写法）。
- 姓名双校验 `valid_free_name`（常见姓氏表 + 停用字表），置信度压到 0.70~0.80：**只负责召回，级别仍由评分公式决定**；
  `address_free` 用零宽断言把句中的「住在/位于/地址：」排除在捕获区间外，脱敏区间不含前缀。
- 测试：`tests/test_identify.py` 新增自由文本人名/地址正反例 3 个（含「系统反馈接口超时」这类普通词不误报）。

### 实测

- **200 条 weibo_ner 自由文本压力集**：纯 L1 准确率 **0.0% → 52.5%**（Micro-F1 0.000 → 0.634，人名覆盖 96/109），
  再叠 NER 为 **90.0% / 0.942**；
- **351 条主评测集**：L1 列准确率保持 **94.0%**、类别 Micro-F1 **0.864 → 0.887**（多出的 FP 都是「示例数据里出现人名」的良性样本，
  接 L2 后仍 99.7%）；开 NER 的 Micro-F1 同步 0.940 → **0.954**。
- 地址类未见回落：压力集里的地名多是湖泊/国家等非标准行政区，规则本就不认，仍由 NER 承担（口径见 `docs/NER探针报告.md`）。

### 验证

- `cd server && python -m pytest -o addopts="" -q` → **271 passed, 1 skipped**（272 个用例）；
- `python -m app.evaluate --dataset eval/ner_stress.jsonl` → 52.5%；加 `FLOWMASK_ENABLE_NER=1` 后 90.0%。

## FlowMask v2 增补（未发版）—— L3 指令微调：裁判准确率 60.0% → 76.2% · 2026-10-21

### 新增

- `server/l3_training/`：L3 裁判的指令微调训练侧
  - `labels.py`：四级 + 十类标签契约，模板理由（不走模型，避免幻觉当监督信号）；
  - `dataset.py`：评测集金标 → 指令样本（351 条，train 316 / val 35，按内容去重）；
  - `train.py`：手写 LoRA 训练循环（prompt 部分 `labels=-100`，只在目标 JSON 上算损失）、
    `dry-run` 数据体检、`merge` 把 adapter 合并成完整权重；
  - `__main__.py` / `README.md`：`dataset / inspect / dry-run / train / merge` 五个子命令。
- 训练与推理共用 `l3_service.backends.INSTRUCT_PROMPT` 与同一行 JSON 契约，合并后的权重
  可由 `FLOWMASK_L3_MODE=instruct` 直接加载，线上代码零改动。

### 实测

| 模型 | 分级准确率 | L3 | L2 | L1 | SAFE | 均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen2.5-1.5B-Instruct 零样本 | 60.0% | 60% | 35% | 100% | 45% | 918 ms |
| LoRA 微调（1 epoch / 74.5 s / GPU） | **76.2%** | **90%** | **80%** | 45% | **90%** | 1298 ms |

- 端到端（351 条 + L2 真模型）：默认配置仍 **99.7%**、高危漏检 0.0%、安全误报 0.0%；
- 诚实结论：裁判单任务涨 16.2 个点，但管道里 L1+L2 已经 99.7%，让 L3 覆盖级别会把准确率拉到 91.2%
  （L1 被抬中危），因此默认保持「L3 只解释/兜底」，微调权重用于自由文本与解释质量的可选升级。

### 验证

- `cd server && python -m pytest -o addopts="" -q` → **268 passed, 1 skipped**（269 个用例）；
- `python -m l3_training dataset && python -m l3_training dry-run` → 351 条、四个级别齐、目标全部可解析；
- 对比脚本：分层抽样 80 条分别打基座 8092 与微调 8093 的 `/v1/judge`（准确率 60.0% → 76.2%）。

  - 需要**管理员权限**：未提权时启动即打印提示，`source=live` 直接以可读错误退出（不是"跑起来却抓不到包"）；
  - 无多队列 / CPU 绑定 / 内核剪枝：配置项照旧可解析，只记一条日志说明被忽略，`filter_kernel` 恒为 false。

  客户端因此不会出现"点了必然失败"的入口。
- **平台判断下沉到采集层**：入口不再用 `runtime.GOOS != "linux"` 拦一道，改由 `capture` 层按平台给出实现或明确错误
  （`live_other.go` 的 build tag 收窄为 `!linux && !windows`），避免"实现有了但入口仍拒绝"的分叉。

### 修复（采集端 0.24.0）

- **本机抓包"莫名正常结束"（隐蔽 bug）**：`recv` 因超时返回失败后读 `WSAGetLastError`，而该函数懒解析时
  会先执行 `GetProcAddress` 并覆盖当前线程 last-error，于是读到 0（"The operation completed successfully."）。
  后果是采集源在第一次静默超时后就结束，日志只有一行
  `[app] 采集源结束: The operation completed successfully.`，看起来像跑完了，极难排查。
  修法：`WSAStartup` 之后**预解析** `recv` / `WSAGetLastError` 两个符号，并把 `errno==0` 归类为"可重试"
  （计数 + 首次打印一条日志）；单测 `TestRecvDisposition` 锁定该行为。

### 已知限制（已写入《双模式设计文档》4.6 节）

- 必须先 `WSAStartup`；标准库 `syscall.Recvfrom` 在 `SIO_RCVALL` 套接字上不可用，必须直接调用 `ws2_32!recv`；
- 原始套接字交付的是纯 IP 报文，需补 14 字节合成以太头 → **本机模式拿不到真实 MAC 地址**；**抓不到 ARP**；
- **抓不到 127.0.0.1 回环流量**：本机若走本地代理（实测本机 hosts 把 `github.com` 指向 `127.0.0.1`），
  这部分流量完全看不到；要覆盖只能另上 Npcap 后端（未排期，属破坏性依赖变更）；
- 只支持 IPv4；`Stats().Drops` 只统计"缓冲不足导致的截断"，不代表网卡丢弃（Windows 没有 `PACKET_STATISTICS` 等价物）。

## v0.23.0（采集端）—— 离线回放可用（本机 Windows 分析 pcap）· 2026-09-28

> 代表性提交：`1ddce2b`（feat(app): 离线回放可用（采集端 0.23.0））。
> 目标：让采集端在 **Windows 本机** 直接回放 pcap 并给出分析结果，对应《双模式设计文档》的 **M3（本机离线分析）**。
> 修复前实测现象：`source = "replay"` 启动后进程「闪一下就没」，`/api/v1/traffic/now` 连不上，`netmon.db` 只有空表结构。

### 修复（采集端 0.23.0）

- **回放结束不再退出进程**：`runOffline` 在数据源耗尽（EOF/ctx 取消）后做一次收尾聚合、落盘残留会话，
  随后阻塞等待 `ctx.Done()`，HTTP 服务继续可用——离线结果可以在界面上自由查看，直到用户主动退出。
  修复前 `App.Run` 在报文通道关闭后直接 `return nil`，`main` 随即 `httpSrv.Shutdown` + 退出。
- **离线时间基准改为 pcap 报文时间**：新增数据时钟 `offlineClock`（`advance(pkt, tick)` / `final()`），
  聚合按报文时间戳跨满一个 `core.tick_ms` 触发，而不是按墙钟 `time.Ticker`。
  修复前回放 3 秒 pcap 只产生约 3 个墙钟周期，且 `Table.Expire(now)` 拿 2026 年的墙钟去比对 pcap 历史时间，
  所有会话被一次性硬超时——`metrics.jsonl` 近乎为空、会话时间线错误。
- **离线收尾会落盘残留会话**：回放完成后把 `Table.Snapshot()` 里仍未过期的会话写入存储，
  避免「短 pcap 只有已关闭会话、active 会话全丢」。

### 新增（采集端 0.23.0）

- **配置键 `[core] offline`**（布尔，默认 `false`）：开启后按 pcap 报文时间推进聚合，回放完成后不退出。
  仅 `source = "replay"` 时有意义；在线（live/synthetic）路径行为完全不变。
- **命令行覆盖参数**：`-replay-file <path>`（覆盖 `capture.replay_file`）与 `-offline`（开启离线模式）。
  优先级高于配置文件；`-offline=false` 不会反手关掉配置里已开启的 `true`。
  这样 Windows 客户端可以直接用参数启动同一个采集端二进制，不必生成临时 config.toml。
- 启动日志增加 `offline=%v` 字段，并在回放完成时打印一行摘要：
  `[app] 离线回放完成: 报文=N 残留会话落盘=M 数据时间=[起, 止]；HTTP 服务继续可用，等待退出信号`。

### 使用方式（采集端 0.23.0）

```bash
# 方式一：命令行直接指定 pcap（推荐，Windows 客户端即用这种方式拉起采集端）
netmon.exe -replay-file D:\captures\sample.pcap -offline

# 方式二：配置文件
# [core]
# source      = "replay"
# offline     = true
# [capture]
# replay_file = "D:/captures/sample.pcap"
netmon -config config.toml
```

回放结束后访问 `http://localhost:8080/api/v1/traffic/now`、`/api/v1/sessions`、`/metrics` 仍可读到离线结果。

### 已知限制（采集端 0.23.0）

- **采样密度等于 pcap 时间跨度**：回放 3 秒 pcap 得到约 3 个聚合采样点。若需要固定采样密度，后续另设参数。
- 离线模式不做墙钟超时，`retention_hours` 对回放数据的时间判断同样基于数据时间。
- Windows 侧仅支持 **离线分析**；Windows **实时抓包（M2）** 仍待 spike 验证，`source = "live"` 在 Windows 上依旧直接报错。
- 客户端尚未提供「本机打开 pcap」入口（后续 `start_local_replay`），当前需手工用参数启动采集端。

  核不够时按顺序循环复用；读不到列表或 `sched_setaffinity` 失败**只打印一条日志并继续**，不影响抓包。
  单队列（`readers = 1`）不绑定 —— 读取发生在调用方 goroutine 上，绑它没有意义。
- 启动日志会写明绑定结果：`[capture] 多队列 CPU 绑定已启用：reader0→CPU0 reader1→CPU1 …`；
  能力上报新增 `capture.cpupin`（客户端的能力列表里可见）。

## v0.20.0（采集端）/ v0.12.8（客户端）—— 内核级过滤剪枝（保守超集，只剪枝不误丢） · 2026-09-22

### 新增（采集端 0.20.0）

- **过滤下沉到内核**：`live` 模式下，`capture.filter` 会被编译成一段经典 BPF 程序，
  经 `SO_ATTACH_FILTER` 挂到每个 AF_PACKET 套接字上（多队列时每个队列各挂一份），

  - 能精确判断的做精确判断：`ip` / `ip6` / `arp`、`[src|dst] host`、`[src|dst] net`，

## v0.17.0（采集端）/ v0.12.4（客户端）—— 一键升级入口与多队列采集 · 2026-09-19

### 新增（采集端 0.17.0）

## v0.15.0 —— 采集层优化：缓冲复用 / 降低排队延迟 / 真实丢包统计 · 2026-09-19

### 优化

- **读缓冲复用**：`live` 抓包原先每个包都分配 64KB 读缓冲（外加一次负载拷贝），现在用 `sync.Pool` 复用读缓冲，
  每包只剩一次必要拷贝，高流量下 GC 压力显著下降。
- **跳过内核排队（PACKET_QDISC_BYPASS）**：抓包套接字设置该选项后，报文不再经过内核 qdisc 排队，
  减少一层延迟与排队丢包（Linux 3.14+；失败不影响启动）。
- **内核接收缓冲**：`SO_RCVBUF` 从 4MB 提到 8MB，进一步降低突发流量丢包概率。
- **丢包统计更真实**：改为读取内核侧统计 `PACKET_STATISTICS`（每 128 个包查询一次，避免每包系统调用），
  `/api/v1/traffic/now` 的 `drop_packets`/`drop_rate` 从此反映**内核真实丢包**，而不是只在读取出错时计数。

## v0.5.1 —— 告警引擎（V2 能力线首个里程碑）· 2026-09-09

### 新增

- **告警引擎（Linux 端，Go）**
  - 新增 `internal/alert` 包：阈值 + 持续时长状态机，持续超过阈值 N 秒才触发，指标回落后自动产生恢复事件；
  - 支持四类规则：带宽 `traffic.bps`、包速率 `traffic.pps`、并发连接 `traffic.conns`、丢包 `traffic.drops`；
  - 事件历史上限 200 条（环形），并发安全；
  - 触发时可通过 Webhook 通知（POST JSON，5 秒超时，失败仅记日志不阻塞采集）。
- **配置 `[alert]` 段**（默认关闭，不影响既有行为）：

```toml
[alert]
enabled = true
bps_threshold = 100000000   # 100 Mb/s 时告警，0 表示该规则不启用
bps_for_secs = 30           # 持续 30 秒才触发
pps_threshold = 0
conns_threshold = 0
drops_threshold = 0
webhook = ""                # 可选：钉钉/企业微信机器人等
```

- **REST 接口**：`GET /api/v1/alerts?status=firing|resolved|all`，返回 `{total, items[]}`，事件字段包含 `rule_id / series / value / threshold / status / started_at / resolved_at / notified`；
- **MeTD 客户端**：连接后每 5 秒查询触发中的告警，主界面顶部显示红色告警横幅（规则、指标、当前值与阈值）。

### 变更

- 主循环 `app.TickOnce` 在每个聚合周期后评估告警，事件通过日志与 API 暴露；
- 版本号：Linux 端保持 0.x 主线，客户端 MeTD 升至 `0.5.1`。

### 验证

- 新增测试：告警状态机（防抖触发/恢复/缺失指标/历史环上限）、通知仅触发一次、配置解析、`/api/v1/alerts` 接口；
- `go vet ./...`、`go test ./...` 全绿；客户端 15 个前端单测全绿。
